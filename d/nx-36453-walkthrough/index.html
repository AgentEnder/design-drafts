00Orientation

Two problems in how Nx prints task output on CI, which only compose into the intended result if they land together.

4693. output.logCommandOutput is the only emitter of GitHub Actions ::group:: folds, and it is reached only through LifeCycle.printTaskTerminalOutput. But NX_BATCH_MODE forced NX_STREAM_OUTPUT for every task in the run, and streamed tasks write straight to stdout without ever calling that method. Nx shipped log grouping and then turned it off for itself.

4692. The static life cycles printed every task's full output — no status filter — so successes and cache hits dumped their whole logs. CI and coding agents get this renderer; humans on the dynamic renderer have had successes collapsed for years.

Why together

4693 alone makes CI logs larger — every task suddenly folded, with its full body. 4692 alone does not touch Nx's own CI at all, because under batch mode its tasks never reach printTaskTerminalOutput. The measured result of both is 66× less stdout on a green run (205,452 B → 3,083 B over 31 cached tasks).

01The coupling: batch mode vs. log grouping

A ::group:: fold needs a task's output as one contiguous block. Streaming cannot provide that — batch mode also sets NX_PREFIX_OUTPUT, which interleaves parallel tasks line by line. So where grouping applies, batch mode's implicit streaming backs off. 

const batchMode = process.env.NX_BATCH_MODE === 'true' || nxArgs.batch;
if (nxArgs.outputStyle == 'stream' || (batchMode && !isLogGroupingEnabled())) {
  process.env.NX_STREAM_OUTPUT = 'true';
  process.env.NX_PREFIX_OUTPUT = 'true';
}

The fix is at the env-var source rather than at the three streaming consumers, so the invariant has one home. Every escape hatch still works: an explicit --output-style=stream wins, NX_SKIP_LOG_GROUPING=true disables folds, an active TUI still streams, and continuous/long-running tasks still stream via the existing longRunningTask branch of shouldStreamOutput.

02The output-style vocabulary

Collapsing is a new style, not a new meaning for an existing one. An earlier revision made static collapse and added static-full to get the old behavior back; that silently redefined a documented enum value people have committed in workflow files. This inverts it.

StylePrints
staticevery task in full, whatever its status — unchanged from what it has always meant
static-failures-onlyfailures in full; successes and cache hits collapse to one ✔ line
Why this works

Nothing assigns outputStyle a default. shouldUseDynamicLifeCycle returns false for non-TTY / isCI() / batch mode and the life cycle is constructed with outputStyle === undefined. So "the default" and "an explicit static" are distinguishable values, which is the entire basis for this design. The default still changes what CI prints — that is 4692's point — but the meaning of a flag does not. Net against master, the only user-visible surface change is one added enum value.

Two predicates are shared rather than re-derived, because three call sites have to agree and the batch renderer not having one is precisely how --output-style stopped applying there (see §07).

03The static life cycles

Both life cycles gained the same shape: a full-output branch, an early return for statuses that have nothing worth showing, and a collapsed one-line summary for everything else. 

if (this.printsFullOutput || taskStatus === 'failure') {
  output.logCommandOutput(args.join(' '), taskStatus, terminalOutput);
  return;
}
if (taskStatus === 'skipped' || taskStatus === 'stopped') return;  // named in the summary
this.collapsedTasks++;
output.logCommandSummary(args.join(' '), taskStatus);

logCommandSummary keeps the existing status suffixes — [local cache], [remote cache], [existing outputs match the cache, left as is] — so a cache hit stays traceable without carrying its log.

Why CollapsibleTaskStatus is a type, not a convention

logCommandSummary accepts Extract<TaskStatus, 'success' | 'local-cache' | 'local-cache-kept-existing' | 'remote-cache'>. The call sites narrow into it by exhaustion, so adding a new TaskStatus becomes a compile error at exactly the two places that must decide what to do about it, rather than silently falling through to a collapsed line.

Run-one differs deliberately in one place: the initiating task always prints in full even on success, because printing nothing for nx build myapp would be surprising. Only its dependency tasks collapse.

04Stopped tasks, and the "Successfully ran" lie

A task ending stopped fell through the endTasks status chain unnoticed, so a run interrupted mid-flight with no outright failures still reported "Successfully ran…". didCommandComplete and the TUI summary already disagreed with that.

inlinein the summaryoutput recoverable
success / cache hit✔ linecounted in the hint--verbose / static
stoppednothingnamed individually--verbose / static
skippednothingnamed individuallynever ran
failurefull outputnamed individuallyalways shown
Why names for one and a count for the other

For successes you only need "did everything pass", so 30 identical lines are noise. For a stopped run you need "which ones did not finish", because that is where you resume. Relatedly, skipped never reaches endTasks — the orchestrator filters it before reporting — so it is derived by subtracting completed tasks from all tasks, while stopped arrives normally and gets a real bucket.

A run containing a stopped task is titled "did not complete" rather than "failed" (nothing failed) or "Successfully ran" (it did not). The withheld-output hint counts stopped tasks too, so a stopped-only run still says partial output exists behind --verbose.

05Line-state tracking in CLIOutput

Task output does not reliably end in a newline, and two new writers must begin at column 0. GitHub only honors a workflow command at the start of a line, so an ::endgroup:: glued onto a task's last line never closes the fold and swallows everything after it: 

Warning: command "jest --passWithNoTests" exited with non-zero status code::endgroup::

CLIOutput now tracks whether stdout sits at a line start, and writers ask for one via ensureLineStart() rather than blindly appending (which added blank lines and regressed nine TUI snapshots when tried).

The subtle part — why the flag is trustworthy

atLineStart asserts a global property from a class-local flag, so anything writing to process.stdout another way makes it stale. Two things make it hold:

Forked-task streaming pipes through addPrefixTransformer, whose formatPrefixedLines re-emits output one whole line at a time and appends EOL to every line — even when the source chunk had none. That path can never leave the cursor mid-line. Batch output is forwarded raw, so it can, and it now goes through writeTaskOutputChunk, which couples the write to the flag update. writeToStream also tracks stderr, since the two share one cursor wherever this matters.

The Buffer is written through undecoded, so a chunk splitting a multi-byte character is not mangled; 0x0a can never be a UTF-8 continuation byte, so the last byte alone answers "did this end in a newline".

06Batch capture goes to disk

Under grouping, a batch worker's live output is held back — forwarding it would print the body once outside the fold (defeating it) and once inside. What is held back has to go somewhere.

Why a file and not a string

A batch is long-lived — Gradle runs one for the whole command — and its output has no bound. capturedOutput += chunk grows without limit and eventually exceeds the maximum length of a JS string. An earlier revision capped it at 1 MB and kept the tail, which meant a compiler batch lost the head where its first, non-cascading errors are.

It now streams to <workspace-data>/batch-outputs/<executor>-<pid>-<n>.log. Nothing is capped or truncated. Writes are synchronous so the file is complete the moment the batch ends, with no flush to sequence against the read that renders it — a WriteStream would have needed an awaited close threaded through the catch path.

The read side matters just as much: copyFileToStream copies through a fixed 64 KB buffer rather than reading the file into a string, which would reintroduce the exact limit the file was meant to avoid. It pushes each chunk through writeTaskOutputChunk, so the copy loop keeps correct line tracking and the trailing ::endgroup:: still lands at column 0.

07Batch rendering: the style decides

Because the live copy was suppressed, whatever is rendered at batch end is the only copy — which is why the requested --output-style has to reach this path rather than stopping at the life cycle. It previously did not: printBatchFold wrote through the output singleton directly and never called lifeCycle.printTaskTerminalOutput, so the style was ignored in both directions.

Batch outcomestatic / --verbosefailures-only (default)
succeedswhole batch log, one foldper-task ✔ lines
failswhole batch log, one foldfailing tasks full, successes ✔
crashes / stoppedwhole batch log, one foldwhole batch log, one fold
Why the bottom row ignores the style

On that path the worker died without reporting results, so every task is marked stopped or failed whether or not it finished — task identity is unknown and the log is the only record of what got through. Routing it per-task would also print nothing at all, because both life cycles drop stopped output by default.

The fold is labelled with the executor and a run-unique id rather than an arbitrary task, since the same executor can run several batches; each task then prints a pointer line at it.

10Known gaps — reviewer attention here

@nx/gradle crash diagnostics

Gradle catches its own crash, backfills terminalOutput: e.toString() per task and resolves rather than rejecting. So it takes the per-task path, and its real diagnostic — the build log and the Gradlew batch failed error, both on the worker's streams — is not printed under the failures-only default. The root-cause fix is in this repo and small: gradle-batch.impl.ts should backfill the actual diagnostic instead of e.toString(). Filed separately rather than widening this PR.

Pre-existing, not widened here

Task output is written verbatim inside a fold, so a build log containing a line beginning ::endgroup:: or ::error:: is interpreted by GitHub as a workflow command. Identical at base. A fix would escape leading :: sequences in fold bodies.

CI flake, not a regression

e2e-react:e2e-ci--src/react-package.test.ts failed on an earlier head: the rollup build succeeded (created …/childlib… in 2s) and the harness then timed out at 300 s on a child that never exited. Nx Cloud puts that task's historical flakiness at 27% and classified the run flaky_task; the failing line is a bare runCLI(build …) with no output assertion, and e2e-react is untouched by this PR.
